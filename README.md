# sprag

> AI 도구 통합을 **플러그인으로 관리하는 확장 가능한 터미널 플랫폼**.

[pinion](https://github.com/newmassrael) 프레임워크 기반.

## 목적

sprag의 목적은 **AI 도구 통합을 플러그인처럼 붙였다 뗐다 하며 관리하는 확장 가능한 플랫폼**을 만드는 것이다.

- **코어(불변)**: 터미널 멀티플렉서 + 셀 격자 scene-as-data + 플러그인 확장 API
- **플러그인(가변)**: 특정 AI 도구 어댑터, AI↔AI 오케스트레이션 루프, 비용/라우팅 정책, copy-mode 등 — 목적에 맞게 붙이고 뗀다
- **존재 이유**: AI 도구 생태계는 빠르게 변한다. 코어를 다시 쓰지 않고 **플러그인을 추가·교체·제거하며 적응**한다 (open for extension, closed for modification).

### 핵심 가치 (불변식 — 절대 타협 없음)

**AI는 화면을 픽셀이 아니라 구조화된 데이터로 읽고 제어한다.** 이것은 플랫폼의 핵심 목적이자, 코어와 **모든 플러그인이 반드시 지켜야 하는 가치**다. 어떤 기능을 플러그인으로 추가하든 이 원칙(scene-as-data, no pixels)을 위반해서는 안 된다.

오케스트레이션 루프·비용 최적화 같은 것은 이 가치 위에 얹는 **교체 가능한 플러그인**일 뿐이지만, "데이터로 읽기"는 교체 대상이 아니라 플랫폼이 존재하는 이유의 일부다.

## 한 줄 정의 (토대)

tmux처럼 여러 터미널을 한 화면에서 관리하되, 각 pane의 내용을 픽셀이 아니라 셀 단위 데이터로 노출한다. 이 구조화된 데이터가 플러그인이 AI 도구를 읽고 제어하는 기반이 된다.

## 왜 (tmux로는 안 되는 것)

tmux 안에서 AI CLI(claude, aider 등)를 돌릴 수는 있으나, (1) 바깥에서 상태를 알 방법이 화면 스크래핑뿐이고 (2) 기능 확장은 코어를 건드려야 한다. sprag은 터미널 출력을 질의 가능한 데이터로 만들고, 그 위에 기능을 플러그인으로 얹을 확장점을 제공해 이 두 벽을 동시에 없앤다.

## 핵심 설계

```
[OS 의사터미널: forkpty / Windows ConPTY]   <- 불투명(opaque): 프로세스 I/O만
        | 바이트 스트림
        v
[VT 파서: 검증된 라이브러리 임베드]          <- 바이트를 셀 격자로 해석
        | 셀 격자 (글자, 색, 속성, 커서)
        v
[코어: scene-as-data + 플러그인 확장 API]    <- 안정적 토대
        |
   +----+--------------------------+
   v                                v
[플러그인들]                    [렌더: TUI 셀 / GPU 창]
 AI 어댑터 · 오케스트레이션 루프 ·
 비용/라우팅 · copy-mode ...
```

PTY(프로세스 입출력)는 불투명하게 두되, VT 파서가 해석한 셀 격자는 구조화 데이터로 노출하고, 그 위에 플러그인이 **동일한 확장 API**로 기능을 얹는다.

## 확장 API (플러그인 계약) — 코어의 최우선 설계 과제

플랫폼에서 가장 중요한 설계 대상. 플러그인은 다음을 통해 코어와 상호작용한다(잠정):

- scene-as-data **읽기**(query): pane 셀 격자·커서·스크롤백·레이아웃
- 입력/이벤트 **주입**(invoke): 키 주입, 명령 실행 — **주입 성공은 전달 보장이 아니다.** 쓰기는
  pty가 받은 시점에 성공한다. 시작 중인 TUI는 그것을 읽고 버린다. 되읽기로 확인하는 경로가
  따로 있다(`deliver`)
- pane 생명주기 **훅**: 생성·실행·종료 이벤트 구독
- **감독**(supervise): pane 속 에이전트가 무엇을 하는지 **레벨로 pull** — 상태, 그 답을 낸
  **권위**(프로세스 자기보고 = 정확 / 화면 스크래핑 = 근사), 게시된 변화 수, 그리고 막혀 있다면
  **무엇을 묻고 있는지**(번호 붙은 선택지) — 데몬의 단일 판정을 그대로
- UI **기여**: 패널/위젯/단축키/명령 등록

pinion의 RPC(query/intervene/invoke/snapshot)와 External 계약이 이 인터페이스의 토대가 된다.

## 기능 범위

**코어 (불변 토대)**

- 단일 pane I/O -> 셀 격자 데이터 노출
- 멀티플렉싱: split/resize/focus, 탭·세션, pane 생명주기
- 플러그인 호스트 + 확장 API
- 렌더: TUI 셀 / GPU 창

**플러그인 (예시 — 붙였다 뗐다)**

- AI 도구 어댑터 (claude, aider, ... 도구별)
- AI↔AI 오케스트레이션 루프 (가드레일: 종료조건·깊이·비용 상한)
- 비용/라우팅 정책 (구독 정액 vs API 종량 선택)
- copy-mode/선택, 상태바, 스크롤백 뷰 등

## 비기능 요구사항

- 플랫폼: **현재 Unix 전용** — Linux에서 검증, macOS는 CI가 빌드한다(`.github/workflows/ci.yml`).
  Windows(ConPTY)는 목표이나 **아직 빌드되지 않는다**: 막는 것은 pty가 아니라 전송 계층으로,
  wire가 Unix 도메인 소켓이다(`sprag-rpc`/`sprag-client`/`sprag-peer`, 27곳). 먼저 그 자리에
  플랫폼별 팔을 가진 로컬 스트림 추상이 필요하다
- VT 호환성: 파서 직접 구현 금지, 검증된 라이브러리 임베드 (최대 리스크 지점)
- 성능: 스크롤백/대용량 출력 렌더 가상화
- 안전: AI 자동 루프 플러그인의 비용 폭주·무한 루프 방지를 1급 요구로

## 제약 / 전제

- pinion 의존 (이 앱은 pinion의 소비자이자 dogfood)
- **플러그인 확장 API 설계가 코어의 최우선 과제** (PTY/셀 격자보다 우선)
- 선결 과제(pinion 측): 셀 격자 프리미티브(예: `Scene::TextGrid`) + 키 입력 인코딩 taxonomy 확정

## 범위 밖

- 헤드리스 JSON이 있는 도구를 굳이 화면 파싱하는 것
- 완전한 xterm 100% 호환 (MVP 단계)
- 특정 플러그인(루프·비용 등)을 코어에 하드코딩하는 것

## 이름

"sprag" = 원웨이(스프래그) 클러치의 부품으로, 한 방향 회전만 물려 전달하고 역방향은 잠근다. pinion(작은 기어)과 같은 기계 계열의 이름이자, 코어가 플러그인을 물려 돌린다는 비유.

레지스트리: GitHub `newmassrael/sprag`, crates.io `sprag` 모두 현재 미선점 상태에서 확보.

## 상태

walking-skeleton 수직 슬라이스 진행 중. **PTY → VT 에뮬레이터 → 셀 격자 → pinion `Scene::TextGrid` → `scene/snapshot`** 데이터 경로가 헤드리스(무-GPU)로 동작한다. 레이어별 크레이트:

- `sprag-vt` — termwiz 기반 에뮬레이터 (`VtPort` 뒤로 격리)
- `sprag-grid` — Screen → pinion `GridBuffer` 투영 (pinion-core만 의존)
- `sprag-terminal` — PTY 프로듀서 (에뮬레이터 소유, pinion 비의존)
- `sprag-host` — scene 조립 + `scene/snapshot` JSON-RPC 서버 (`sprag-term` 바이너리, 현재 읽기 전용)

멀티플렉싱·입력 인코딩·플러그인 호스트·GUI 렌더는 미착수.
